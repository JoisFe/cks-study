# /grade — 답안 채점

사용자가 방금 푼 답안을 정답 루브릭 대비로 채점한다. 이 스킬은 **한 문제(또는 여러 문제) 단위 정밀 채점**용이다. 2시간 풀 세트의 총점/합격 판정은 `/mock-exam`(exam-proctor 위임)이 담당하고, 이 스킬은 그 안에서 개별 Task를 세밀하게 뜯어볼 때도 호출된다. 아래 절차를 순서대로 따른다.

## 역할

제출한 답안을 정답 루브릭 대비 **결과 상태 기반 부분점수**로 채점하고 감점 이유·교정안·검증 명령을 제시한다.

## 하지 않는 것

- 2시간 풀세트 총점·합격 판정 (→ `/mock-exam`)
- 후한 채점 — "의도"가 아닌 "최종 상태"로 판정
- 문제 특정 없이 추측 채점 (먼저 어떤 Task인지 확정)

## 절차

1. **어떤 Task/문제에 대한 답인지부터 확정한다.**
   - 사용자가 세트·Task 번호를 명시했으면(예: "모의고사 2회 Task 10") 해당 파일을 Read로 연다: `mock-exams/mock-exam-0N.md` 또는 개념서 예제라면 `domains/*.md`.
   - 명시하지 않았으면, 답안 내용(리소스 종류, namespace, 파일 경로, 플래그)으로 어느 문제인지 추론해 후보를 제시하고 사용자에게 확인받는다. 엉뚱한 문제 기준으로 채점하면 채점 자체가 무의미하다.
   - 문제를 특정했으면 그 Task의 **문제 본문 + 해설(details 접기 안의 "정답 및 해설", "부분점수 포인트")**을 읽어 채점 루브릭을 확보한다. 개념서 예제라 명시적 배점표가 없으면, 문제가 요구한 요건을 항목으로 분해해 즉석 루브릭을 만든다.

2. **정답 루브릭 대비 부분 점수로 채점한다. 감점 요인을 구체적으로 짚는다.**
   - 실전 CKS는 **결과 상태 기반 자동 채점 + 부분점수**다. 이 방식을 그대로 흉내 낸다: 요건을 하위 항목으로 쪼개고, 각 항목이 **최종 상태로 충족되는지**로 판정한다 — 명령이 맞아 보여도 결과가 틀리면(Pod가 Pending, 파일 미존재, 포트가 여전히 열림, NetworkPolicy가 트래픽을 실제로 못 막음) 그 항목은 0점.
   - 각 하위 항목을 `[O] / [X] / [부분]`으로 표시하고, X·부분마다 **왜 감점인지**를 한 줄로 명확히 쓴다. 예: "egress에 DNS(53/UDP·TCP)를 안 열어 default-deny 때문에 이름 해석 실패 → DB 접속 항목도 연쇄 0점", "`readOnlyRootFilesystem: true`는 넣었으나 `allowPrivilegeEscalation: false` 누락", "apiserver 플래그는 맞으나 static pod manifest 저장 후 kube-apiserver가 재기동 실패(오타)로 상태 미반영".
   - 흔한 감점 함정을 반드시 점검: 잘못된 namespace / 파일을 지정 경로(`/opt/course/<task>/...`)에 정확히 저장했는지 / 리소스 이름 철자 / `kubectl config use-context` 누락 / 적용(apply)까지 했는지 / apiserver·kubelet 설정 변경 후 실제 재기동·반영 여부.
   - 하위 항목 점수를 합산해 **해당 Task의 획득 점수 / 배점**을 낸다(예: 3항목 균등 배분 7% → 2항목 정답 시 약 4.7%). 여러 문제를 한꺼번에 냈으면 Task별로 표를 만들고 소계를 낸다.

3. **개선된 정답 예시와 검증 명령을 제시한다.**
   - 감점난 항목에 대해 **복사 후 즉시 실행 가능한** 교정 YAML/명령을 준다(v1.35, containerd, Ubuntu 노드 기준). 폐기된 메커니즘(PSP 등)은 절대 쓰지 않는다.
   - 사용자가 스스로 결과를 확인할 수 있는 **검증 명령**을 함께 준다. 예:
     - NetworkPolicy: `kubectl exec <pod> -- wget -qO- --timeout=2 <target>` 로 허용/차단 실제 확인.
     - RBAC: `kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa>`.
     - Pod 보안 필드/상태: `kubectl get pod <name> -o jsonpath='{.status.phase}'`, `kubectl get pod <name> -o yaml | grep -A5 securityContext`.
     - 파일/노드 설정: `ls -l /opt/course/<task>/...`, 노드에서 `systemctl is-active <unit>`, `ss -tlnp | grep <port>`.
   - 정답에 이르는 최단 실전 동선(문서 어디를 보고 무엇을 복사하는지)이 있으면 짧게 곁들인다.

4. **감점이 있으면 progress/weak-spots.md에 표준 규약대로 기록을 제안한다.**
   - 감점·오답 항목이 있으면 약점 기록을 제안하고, 사용자가 동의하면 `/Users/jo/cks/progress/weak-spots.md`의 **`§2 약점 로그`** 표에 표준 한 줄을 append 한다(그 파일 §1-1 규약). 열: `날짜 | 도메인 | 토픽 | 유형 | 출처 | 근거 개념서`. 예: `| 2026-07-25 | D1 Cluster Setup | egress DNS(53) 누락 | 부분감점 | grade mock-01 T1 | domains/01-cluster-setup.md |`. 출처는 `grade <세트 T번호>`(개념서 예제면 `grade domains/0N`). 파일은 이미 존재하므로 새로 만들지 않는다.
   - 같은 `도메인+토픽`이 §2에 이미 있으면 새 행 대신 기존 행 토픽 끝에 `(재발 xN)`을 올린다(중복 규칙). `§3 도메인별 현황`은 건드리지 않는다 — 집계는 `/weak-spots` 몫이다.
   - 채점 말미에 다음 행동을 제안한다: 취약 토픽은 `/quiz`로 랩드파이어 반복, 개념이 흔들리면 cks-tutor 에이전트로 복습, 실습 중 막히는 디버깅은 k8s-troubleshooter 에이전트로 위임, 누적 약점은 `/weak-spots`로 조회.

**채점 원칙(항상 상기)**: 후하게 주지 않는다. 실전은 "의도"가 아니라 "결과 상태"만 본다. 명령이 그럴듯해도 최종 상태가 요건을 충족하지 못하면 감점이라는 기준을 일관되게 적용해, 사용자가 시험장에서 겪을 실제 점수에 최대한 가깝게 채점한다.
